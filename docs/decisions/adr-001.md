# ADR-001: In-Memory Task Storage

- **Status:** Accepted
- **Date:** 2026-07-23
- **Topic:** In-memory task storage
- **Applies to:** `app/storage.py`, `app/main.py`, `app/models.py`, `tests/conftest.py`

## 1. Context

The Task Tracker is a minimal FastAPI + Pydantic v2 REST backend built as a
learning project. It exposes CRUD routes for tasks, task comments, and a
`/health` check, and the route handlers are deliberately thin, delegating
persistence to a single storage layer.

The persistence question is: where do tasks live between requests? The project's
goals are to keep setup friction near zero, keep the code readable, and let tests
run fast and in full isolation, not to durably retain data. A task is a small,
self-contained record (`id`, `title`, `description`, `status`, `priority`,
`assignee`, `due_date`, `created_at`, `updated_at`) and comments are task-scoped
records (`id`, `task_id`, `text`, `created_at`).

Current implementation: `app/storage.py` holds tasks in a module-level
dictionary `_tasks: dict[str, TaskResponse]` and comments in
`_task_comments: dict[str, list[TaskCommentResponse]]`. The module owns id
generation (`uuid.uuid4()`) and timestamp bookkeeping. A test-only `_reset()`
clears both dictionaries for isolation between tests.

## 2. Decision

Store tasks and task comments in in-process Python dictionaries keyed by
generated UUID strings, with no database, no ORM, and no disk persistence. All
state lives in memory and is lost when the process restarts. The storage layer
(`app/storage.py`) is the sole owner of these dictionaries, id generation, and
timestamp stamping; route handlers never touch the stores directly. Tests reset
state via `_reset()` before and after each test.

## 3. Alternatives Considered

- **SQLite (file-based, via SQLAlchemy or `sqlite3`).** Durable across restarts,
  still zero external services. Adds an ORM/driver dependency, schema/migration
  concerns, and connection handling that the learning scope does not require.
- **SQLite in-memory (`:memory:`).** Durable-shaped API without a file, but adds
  SQL/ORM machinery for no persistence benefit over a plain dict.
- **Full RDBMS (PostgreSQL, etc.).** Rejected outright: requires a running
  service, connection config, and operational overhead far beyond a minimal
  learning backend.
- **JSON/flat-file persistence.** Would survive restarts, but introduces file
  I/O, serialization, and concurrency/locking questions with little educational
  payoff for this module.
- **Plain dict in memory (chosen).** Simplest possible store; no dependencies,
  no schema, trivially resettable for tests.

## 4. Trade-offs

- **Simplicity vs. durability:** the dict is the least code and the fastest to
  reason about, but every restart wipes all data — acceptable only because
  persistence is a non-goal here.
- **Test speed/isolation vs. realism:** `_reset()` gives instant, fully isolated
  tests against the real store (no mocking), but the tests never exercise a real
  persistence boundary, so they can't catch DB-specific issues.
- **No dependencies vs. no query power:** filtering is done in Python
  (`get_all_tasks` list comprehensions), which is fine for the expected small
  local/demo workload but has no indexing and is O(n) per filter.
- **Single-process correctness vs. concurrency:** a module-level dict is process-
  local. Under multiple workers/processes each would hold its own separate store,
  and there is no locking around read-modify-write in `update_task`. This
  project intentionally runs as a single-process app in documented local and
  Docker commands.

## 5. Consequences

- Data is **ephemeral**: restarting `uvicorn` (or the Docker container) starts
  from an empty store. This is stated in the README and is expected behavior.
- The store is **not shared across processes**: running with more than one worker
  would give inconsistent results, since each process has its own `_tasks`.
  Current documented local and Docker commands run a single process.
- Tests stay fast and isolated via the autouse `_reset()` fixture; no test
  database or fixtures-teardown is needed.
- The storage layer is a clean seam: swapping the dict for a real database later
  means reimplementing `app/storage.py`'s functions without changing the route
  handlers or Pydantic models — provided their signatures stay stable.
- This decision explicitly does **not** add authentication, a database,
  deployment, or production hardening; those remain out of scope.

## 6. Open Questions

No blocking open questions remain for the current course scope. The following
future triggers are documented for later re-evaluation:

- If task volume or query complexity grows beyond small local/demo usage,
  replace list-comprehension filtering with indexed database queries.
- If multi-worker deployment is required, move persistence to a shared external
  store and remove process-local assumptions.
- If durability becomes a requirement, start with SQLite as the lowest-friction
  first step and preserve the storage-layer interface so route handlers remain
  unchanged.
